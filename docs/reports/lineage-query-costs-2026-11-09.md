# Lineage discovery query costs

Decision for [issue 174](https://git.subcult.tv/subculture-collective/arkhiv/issues/174).
Measured November 9, 2026, on disposable data on Kvant. Engine source is `main`
at `2a35471`. This records a decision; it changes no production query.

## Decision

The corpus-wide status aggregate dominates discovery latency, so the smallest
justified optimization is to stop running it once per recording query.

`Store.Search` computes its page in a few milliseconds to a few hundred, then calls
`Status`, whose `AudioCoverage` joins every review, representation and membership
for the collection. An anniversary query spends over 99% of its time there.

Issue 180 should cache the status aggregate per collection for 30 seconds, with one
in-flight computation, and keep the `status` response field. That is compatible
with existing clients and needs no API, schema or index change. The items query and
its count stay uncached, so visibility and totals remain current. The remaining
home-page cost is a separate, smaller item.

## Measurements

The corpus is generated by `TestDiscoveryQueryCosts`: 295,995 catalog records, 297
excluded, 1,200 unavailable, and 295,698 rows in each playback table. It is sized
to the [Lineage baseline](https://git.subcult.tv/PatrickFanella/arkhiv-live-music/src/branch/main/docs/reports/discovery-loading-baseline-2026-11-09.md),
which reported 295,994 imported and 297 excluded. Artist frequency is skewed across
about 12,000 names, and dates span 1965–2025. The anniversary used here matched 771
records; the baseline's matched 837.

Each row is three sequential runs, in milliseconds, through the real `Store` methods
or the exact production SQL.

| Query | Run 1 | Run 2 | Run 3 |
|---|---:|---:|---:|
| Search, home (with status) | 1,632 | 1,608 | 1,583 |
| Search, anniversary (with status) | 1,332 | 1,383 | 1,415 |
| Search, artist (with status) | 1,418 | 1,340 | 1,316 |
| Items SQL only, home | 363 | 375 | 356 |
| Items SQL only, anniversary | 4.2 | 4.1 | 3.6 |
| Items SQL only, artist | 59 | 55 | 54 |
| `Status` | 1,430 | 1,422 | 1,427 |
| `AudioCoverage` alone | 1,334 | 1,243 | 1,286 |
| Facets | 319 | 312 | 302 |
| Calendar, November across all years | 46 | 37 | 47 |
| Detail | 21 | 20 | 21 |

The shape matches production. The baseline measured status at about 3.2 seconds
and an anniversary search at 3.3 seconds, so production is roughly 2.4 times
slower while the status share is the same. Calendar and detail already fit their
budgets here.

## Plans

`EXPLAIN (ANALYZE, BUFFERS)`, PostgreSQL 17 with default memory settings.

**Anniversary items, 2.9 ms.** An index scan on `source_catalog_visible_month_day`
returns 771 rows, then a top-N sort; 782 buffers, no temporary files.

**Home items, 406 ms.** A sequential scan returns all 295,698 visible rows, then the
materialized `filtered` CTE writes about 48,500 temporary pages because it carries
the full `effective` document, only to count rows and take the first 101.

**Audio coverage, 1,349 ms.** Sequential scans of all five tables (295,698 rows
each) feed hash joins and an external merge sort of 24.6 MB for the `DISTINCT`.
Nothing is selective because the query answers a whole-collection question. It
touches about 83,000 shared buffers and writes about 43,000 temporary pages.

## Equivalence

The anniversary query returned a total of 771 through `Store.Search` and through the
production SQL alone, with the same page of 100. Removing the status call from the
request path cannot change results, because `status` is computed separately from
`total` and `items`.

## Checks for issue 180

- Response shape is unchanged. `status` keeps every field for old clients.
- Items and totals stay uncached: an exclusion or correction is reflected in
  `total` and `items` on the next request, even while `status` is up to 30 seconds old.
- The cache is per collection, so one collection's coverage is never served for
  another. Concurrent requests share one computation, and a failed computation is
  not retained.
- Repeat this harness and confirm the anniversary query falls to tens of
  milliseconds with a warm cache.

## Not justified yet

Do not add an advertised lightweight read option, remove the exact total, or raise
timeouts. Trimming the home page's `filtered` CTE so that it does not carry
`effective` would save at most about 370 ms here, and that is worth considering
only if the home budget is still missed after the status change. Full-text search
for a term matching most of the corpus took about 2.1 seconds, but it is outside
the measured baseline scenarios.

## Reproduction and limits

```sh
LINEAGE_QUERY_COST=1 TEST_DATABASE_URL=<disposable> \
  go test ./internal/sourcecatalog -run TestDiscoveryQueryCosts -count=1 -v -timeout 10m
```

The data is synthetic, in a container with tmpfs storage and warm caches on Kvant.
Absolute times are therefore lower bounds for Lineage's host; the production ratio
above comes from the separate browser baseline. Production `EXPLAIN` was not run,
and no preview or production database was touched. Real value distributions and
hash variety may change plan details. Raw plans are retained outside Git under
`~/.local/state/lineage-wave2/spike/`.
